# Pi-Guard Lite 从 0 到落地详细步骤文档

## 1. 文档目的

本文档用于把 **Pi-Guard Lite** 项目从 0 开始到最终落地的全部步骤拆开说明，适合：

- 一个人独立完成项目
- 边做边学
- 预算有限
- 基于树莓派搭建单节点 AI 智能防御系统

本文档默认方案：

- **项目名称**：Pi-Guard Lite
- **硬件形态**：单节点树莓派
- **部署方式**：旁路检测 + 联动现有路由器/OpenWrt 执行
- **预算目标**：800 RMB 内
- **推荐硬件**：二手 Raspberry Pi 4B 4GB

---

## 2. 项目最终目标

你最终要做出来的不是“一个脚本”，而是一套最小可运行的安全防御系统，要求至少具备：

1. 采集网络流量日志
2. 采集系统/服务日志
3. 识别扫描、爆破、异常外联等行为
4. 对事件做规则判断和轻量 AI 风险评分
5. 自动生成防御策略
6. 自动联动现有路由器或防火墙执行封禁
7. 自动进行业务探测
8. 出现误伤时自动回滚
9. 提供最小可视化页面
10. 形成可演示、可部署、可迭代的项目成果

---

## 3. 整体工作分阶段

整个项目建议分为 10 个阶段：

1. 明确范围与约束
2. 采购与准备硬件
3. 设计网络接入方式
4. 安装与初始化操作系统
5. 搭建基础运行环境
6. 完成感知层
7. 完成决策层
8. 完成执行层
9. 完成动态控制层
10. 联调、测试、文档、发布

---

# 第一阶段：明确范围与约束

## 4. 第一步：写清项目边界

### 4.1 你要先明确“不做什么”
为了控制项目复杂度，第一版明确不做：

- 不做多节点集群
- 不做 10Gbps 网关
- 不做大模型本地部署
- 不做 ELK、Kafka、K8s
- 不做复杂 EDR Agent
- 不做长期全量 PCAP 保存
- 不做企业级高可用

### 4.2 你要明确“第一版必须做什么”

- Suricata 流量检测
- 系统日志采集
- 事件标准化
- 规则检测
- AI 风险评分
- 自动封禁
- 自动回滚
- 简单管理页面

### 4.3 输出物
你要先写一个最简单的范围说明，内容包括：

- 项目名称
- 项目目标
- 硬件方案
- 软件栈
- 第一版功能范围
- 不做项

### 4.4 完成标准
- 你自己能在 3 分钟内讲清楚项目做什么、不做什么

---

## 5. 第二步：定义最终验收标准

你必须先决定“做到什么算完成”。

### 5.1 建议验收标准

项目完成时至少满足：

1. 树莓派能稳定运行 24 小时
2. 能采集 Suricata 告警日志
3. 能采集本机或目标主机日志
4. 能识别扫描、爆破、异常外联
5. 每个事件都能生成风险分
6. 高危事件能触发自动封禁
7. 自动封禁后能做业务探测
8. 业务异常时能自动回滚
9. 页面上能看到事件、策略、封禁记录
10. 能拿真实场景演示完整闭环

### 5.2 完成标准
- 你把验收标准单独写成一段清单，后续每一步都围绕它来做

# 第三阶段：设计网络接入方式

## 8. 第五步：确定网络拓扑

### 8.1 你必须先选一种接入方式

#### 方案 A：交换机镜像口
最推荐。

树莓派只做旁路监听，不改原网络路径。

#### 方案 B：路由器日志接入
如果没有镜像口，可以先接入：

- OpenWrt 日志
- DNS 日志
- 防火墙日志

#### 方案 C：本机日志模式
如果什么都没有，可以先拿树莓派自身或一台测试主机做日志输入源。

### 8.2 建议网络结构

```text
Internet -> 路由器/OpenWrt -> 交换机 -> 测试主机
                              \-> 树莓派(镜像流量)
```

### 8.3 你要记录的信息

- 路由器 IP
- 树莓派 IP
- 被保护主机 IP
- 交换机镜像口配置
- 核心业务测试地址

### 8.4 完成标准
- 你画出一张自己的网络连接草图

---

## 9. 第六步：确定联动执行对象

### 9.1 第一版不要试图控制太多设备
只选一个执行对象就行：

- OpenWrt
- 家用路由器（支持 SSH/API）
- 一台 Linux 防火墙主机

### 9.2 你要确认的事情

- 能否 SSH 登录
- 有没有 root 权限
- 能否执行 `iptables` / `nftables` / `ipset`
- 是否可以写临时防火墙规则

### 9.3 完成标准
- 树莓派能从网络上访问目标执行设备

# 第六阶段：完成感知层

## 15. 第十二步：安装并配置 Suricata

### 15.1 目标
让树莓派能够接收镜像流量并输出结构化安全事件。

### 15.2 要完成的事情

1. 安装 Suricata
2. 找到正确的监听网卡
3. 配置 AF_PACKET
4. 启用 `eve.json`
5. 启用必要协议日志：
   - alert
   - dns
   - http
   - tls
   - anomaly
6. 设置日志输出目录
7. 启动并验证服务

### 15.3 你要重点检查

- Suricata 是否正常加载规则
- 是否能看到实时日志输出
- `eve.json` 是否在持续写入

### 15.4 完成标准
- 在有流量的情况下，Suricata 能持续产生日志

---

## 16. 第十三步：制造一批测试流量

### 16.1 为什么必须做
如果没有测试流量，你无法判断 Suricata 是否真的工作。

### 16.2 建议制造的场景

- 用浏览器访问网站
- 用 `ping` 测试主机
- 用 `curl` 请求页面
- 用 `nmap` 对测试主机扫描
- 用错误密码反复 SSH 登录

### 16.3 你要观察什么

- 是否出现扫描告警
- 是否出现认证失败日志
- 是否有 DNS、HTTP、TLS 记录

### 16.4 完成标准
- 至少能稳定触发 2~3 类事件

---

### 18.1 目标

## 19. 第十六步：做特征提取

### 19.1 目标
把事件进一步转成可用于判断和打分的特征。

### 19.2 建议第一版特征

- 单 IP 1 分钟请求数
- 单 IP 登录失败次数
- 单 IP 连接不同端口数
- DNS 查询失败率
- HTTP 4xx/5xx 比例
- 过去 10 分钟同类事件数
- 是否命中黑名单
- 是否命中白名单
- 目标资产重要性

### 19.3 完成标准
- 每条事件可对应生成一组结构化特征

# 第七阶段：完成决策层

## 20. 第十七步：做规则检测引擎

### 20.1 第一版原则
先规则，后 AI。

### 20.2 建议先做的规则

1. SSH 爆破规则
2. 端口扫描规则
3. HTTP 高频访问规则
4. 可疑 DNS 规则
5. 已知恶意 IP/域名规则

### 20.3 规则逻辑示例

- 1 分钟内同一源 IP 访问 50 个以上端口 -> 端口扫描
- 3 分钟内某 IP 登录失败超过 20 次 -> 爆破
- 某域名命中恶意情报列表 -> 高危

### 20.4 完成标准
- 规则检测能对事件输出命中结果和严重等级

---

## 21. 第十八步：建立行为基线

### 21.1 目标
知道“什么是正常”，才能知道“什么是异常”。

### 21.2 第一版基线建议

- 某主机常访问哪些目标 IP
- 某业务平时访问哪些端口
- 某用户通常几点登录
- 某主机平时 DNS 查询频率

### 21.3 如何做

1. 收集一段正常期数据
2. 按 IP、服务、时间窗口统计
3. 存入 SQLite
4. 后续检测时做偏离计算

### 21.4 完成标准
- 能对新事件打出“偏离基线程度”

---

## 22. 第十九步：做 AI 异常检测

### 22.1 第一版原则
只做轻量模型，不做复杂训练平台。

### 22.2 推荐模型

#### Isolation Forest
用于：

- 异常连接行为
- 异常登录模式
- 异常外联

#### LightGBM
用于：

- 风险分类
- 多特征打分

### 22.3 实际落地步骤

1. 在 PC 上收集训练样本
2. 做基础清洗
3. 选择特征列
4. 训练模型
5. 导出模型文件
6. 放到树莓派 `models/`
7. 编写模型加载和推理逻辑

### 22.4 完成标准
- 模型能在树莓派本地加载并输出结果

---

## 23. 第二十步：实现风险评分引擎

### 23.1 目标
把规则结果、基线偏离、AI 结果合成一个分数。

### 23.2 建议评分逻辑

```text
风险分 = 规则得分 + 异常分 + 资产重要性 + 历史重复风险 - 白名单修正
```

### 23.3 风险分级建议

- 0~39：记录
- 40~69：告警
- 70~84：建议封禁
- 85~100：自动封禁

### 23.4 完成标准
- 每个事件都能得到稳定一致的风险等级

---

## 24. 第二十一步：设计策略生成逻辑

### 24.1 第一版策略动作建议

- 只告警
- 记录观察
- 限速
- 临时封禁 IP
- 手工复核标记

### 24.2 策略生成原则

- 白名单优先放行
- 高危资产优先保护
- 尽量使用带 TTL 的临时策略
- 先小范围处置，再考虑升级

### 24.3 完成标准
- 根据风险分，系统能自动输出明确动作

---

# 第九阶段：完成动态控制层

## 28. 第二十五步：实现业务探测

### 28.1 目标
判断新策略是否影响正常业务。

### 28.2 建议探测类型

- HTTP 页面探测

## 29. 第二十六步：实现自动回滚

### 29.1 回滚触发条件建议

- 策略执行后核心 URL 无法访问
- 核心端口无法建立连接
- 连续两次探测失败

### 29.2 回滚逻辑

1. 找到最近执行的策略
2. 判断它是否属于当前探测失败范围
3. 自动执行解封命令
4. 记录回滚原因
5. 通知管理员

### 29.3 完成标准
- 新策略导致业务异常时，系统能自动恢复
