# Pi-Guard Lite 开发规范

本规范从现在开始执行，后续新增代码、配置、脚本、文档都必须遵守。

---

## 1. 总原则

1. 先做最小闭环，再做增强功能
2. 先保证可运行，再追求复杂度
3. 所有关键行为必须可追踪
4. 所有关键参数必须配置化
5. 默认保守，不做高风险自动操作
6. 任何自动封禁都必须支持 TTL 和回滚

---

## 2. 功能实现顺序

后续开发必须按这个顺序推进：

1. 数据输入
2. 事件解析
3. 特征提取
4. 规则判断
5. 风险评分
6. 策略生成
7. 执行器
8. 探测与回滚
9. Web 展示
10. 模型增强

禁止跳过主链路，直接堆高级功能。

---

## 3. 目录规范

### 3.1 代码目录职责固定

- `app/collector/`：只负责采集输入，不做复杂判断
- `app/parser/`：只负责原始数据转结构化对象
- `app/features/`：只负责特征提取
- `app/detector/`：只负责规则和模型判断
- `app/scorer/`：只负责风险评分
- `app/policy/`：只负责策略生成
- `app/executor/`：只负责动作执行
- `app/probe/`：只负责探测和回滚
- `app/web/`：只负责 API 和页面
- `app/common/`：公共模块

### 3.2 禁止事项

- 禁止在 `web` 里直接写数据库业务逻辑
- 禁止在 `collector` 里直接做策略封禁
- 禁止在 `executor` 里做评分逻辑

---

## 4. 代码规范

### 4.1 Python 规范

- Python 版本目标：**3.10+**
- 新代码优先使用类型标注
- 函数必须短小，单一职责
- 不写超长函数，单函数建议不超过 80 行
- 复杂逻辑必须拆分成独立函数

### 4.2 命名规范

- 文件名：小写 + 下划线
- 类名：大驼峰
- 函数名：小写 + 下划线
- 常量名：全大写 + 下划线

### 4.3 注释规范

- 不写废话注释
- 只解释“为什么”
- 输入输出复杂时必须写函数说明

### 4.4 日志规范

必须记录日志的场景：

- 服务启动
- 配置加载
- 数据库初始化
- 新事件接入
- 规则命中
- 风险评分结果
- 策略生成
- 封禁执行
- 解封执行
- 回滚执行
- 异常与失败

禁止直接 `print` 代替日志。

---

## 5. 配置规范

1. 所有地址、阈值、路径必须进配置文件
2. 禁止把 IP、密码、端口硬编码在业务代码
3. 配置文件采用 YAML
4. 所有配置项必须有默认值或示例文件
5. 后续敏感信息优先通过环境变量覆盖

---

## 6. 数据规范

### 6.1 事件对象

所有检测逻辑必须基于统一事件对象，禁止各模块自己定义一套字段。

### 6.2 数据库存储

- 结构化数据入 SQLite
- 原始数据存 `data/raw/`
- 所有表结构变更必须同步更新 SQL 初始化脚本

### 6.3 审计要求

以下动作必须可追踪：

- 封禁
- 解封
- 回滚
- 模型切换
- 白名单变更

---

## 7. 执行安全规范

1. 第一版只允许针对 IP 做临时封禁
2. 默认必须带 TTL
3. 自动封禁前必须经过评分阈值
4. 白名单目标永不自动封禁
5. 新策略执行后必须进入探测流程
6. 探测失败必须允许自动回滚

---

## 8. Web/API 规范

1. `/health` 必须始终可用
2. API 返回结构要稳定
3. 页面只做展示和简单操作，不承载复杂逻辑
4. 管理动作必须留审计记录
5. 后续新增接口必须写到文档

---

## 9. 测试规范

每完成一批功能，至少做这三类测试：

1. 语法/启动测试
2. 模块功能测试
3. 整链路测试

上线前必须补：

4. 误伤测试
5. TTL 过期测试
6. 自动回滚测试

---

## 10. 文档规范

每做完一批实质开发，都要同步更新：

- `docs/工作状态清单.md`
- 配置说明
- 接口说明
- 已知问题

禁止只改代码不更新文档。

---

## 11. 提交规范

后续每次阶段性修改，提交说明必须能回答：

1. 这次加了什么
2. 影响哪些模块
3. 当前还缺什么
4. 是否可运行

建议提交标题格式：

```text
feat: 新增 Suricata 事件读取器
fix: 修复 SQLite 初始化路径问题
docs: 更新工作状态清单
refactor: 拆分风险评分逻辑
```

---

## 12. 完成定义

一个功能只有在同时满足下面条件时，才算“完成”：

1. 代码已写
2. 本地可运行
3. 有日志
4. 有配置
5. 有最基本测试
6. 文档已更新

只写了代码，不算完成。

---

## 13. 当前强制执行的近期目标

下一阶段只允许做以下内容：

1. 统一事件模型
2. Suricata 输入读取
3. Suricata 解析器
4. 第一版特征提取
5. 第一版规则引擎
6. 第一版风险评分

在这批完成前，暂不开发：

- 复杂前端
- 蜜罐
- 多节点
- 图数据库
- 大模型能力

---

## 14. 违规处理原则

如果后续开发出现下面情况，必须回退并修正：

- 硬编码敏感配置
- 模块职责混乱
- 无日志
- 无文档更新
- 自动封禁无 TTL
- 新功能没有最小测试

---

## 15. 执行承诺

从本文件生成起，后续我继续为你开发 Pi-Guard Lite 时，默认遵守本规范。
